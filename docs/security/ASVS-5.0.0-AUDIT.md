## 2. Critical & High Findings


### [ASVS-001] CWE-601: URL Redirection to Untrusted Site ('Open Redirect') / Broken Mobile Return Flow
* **Severity:** **High**
* **ASVS Requirements:** v5.0.0-10.2.2, v5.0.0-2.3.1, v5.0.0-15.3.1
* **Affected Components:**
  - `apps/mobile/src/app/booking/[slug].tsx:L183`
  - `lib/actions/booking.ts:L211-L220`
  - `app/api/payments/return/route.ts:L1-L100`
* **Exact Evidence:** Stripe checkout previously pointed directly to web dashboard or attempted invalid custom-scheme URL. Remediated by creating app/api/payments/return/route.ts which issues an HTTP 302 redirect with Location: `medaura://booking-payment?status=${status}&appointmentId=${appointmentId}`, allowing the in-app browser (WebBrowser.openAuthSessionAsync) to automatically capture the scheme, close the browser, and resume the native app.
* **Attack / Failure Scenario:** A patient completes a payment on their phone. Instead of returning to the native app, they land in an authenticated web session inside a constrained modal browser.
* **Impact:** High UX breakdown, potential double-payment attempts by confused users, and stranded web session state in mobile in-app browser.
* **Recommended Remediation:** RESOLVED: Created app/api/payments/return/route.ts HTTP return bridge and updated lib/actions/booking.ts. Verified via test/payments-return.test.ts.

### Finding ASVS-002: CWE-1021: Improper Restriction of Rendered UI Layers / Permissive Content Security Policy
* **Severity:** **Medium**
* **ASVS Requirements:** v5.0.0-3.4.1, v5.0.0-3.4.2, v5.0.0-1.2.1
* **Affected Files:**
  - `next.config.mjs:L21-L22`
* **Security Boundary Violated:** Browser execution sandbox / Client-side defense-in-depth
* **Exact Code Evidence:** In next.config.mjs:L21-L22, Content-Security-Policy defines `script-src 'self' 'unsafe-inline' https://www.google.com https://www.gstatic.com` and `style-src 'self' 'unsafe-inline'`. While Google reCAPTCHA and Next.js inline scripts necessitate inline execution in standard setups, 'unsafe-inline' weakens protection against stored/DOM XSS.
* **Exploit / Failure Scenario:** If an attacker managed to inject HTML/JS via an unsanitized Markdown/rich-text sink or third-party component, the browser would execute it without nonce verification due to 'unsafe-inline'.
* **Business & Technical Impact:** Reduced defense-in-depth against client-side injection vulnerabilities.
* **Remediation Strategy:** Implement nonce-based Content Security Policy via Next.js middleware using crypto nonces passed via headers and Script components with `nonce` attributes, replacing 'unsafe-inline'.
* **Required Regression Tests:** Automated header regression tests asserting CSP directives and verifying nonce generation per request in production mode.

### Finding ASVS-003: CWE-287: Improper Authentication
* **Severity:** **Medium**
* **ASVS Requirements:** v5.0.0-6.4.1, v5.0.0-6.4.2, v5.0.0-2.3.2
* **Affected Files:**
  - `lib/auth.ts:L68`
  - `lib/actions/booking.ts:L52-L55`
* **Security Boundary Violated:** Identity proofing and account verification boundary
* **Exact Code Evidence:** Unverified accounts were previously not strictly blocked from booking appointments. Remediated by adding production email verification enforcement in lib/actions/booking.ts:L52-L55 when email is configured, throwing ForbiddenError.
* **Exploit / Failure Scenario:** An attacker could register accounts using unverified email addresses owned by third parties.
* **Business & Technical Impact:** Unverified email addresses could pollute the platform.
* **Remediation Strategy:** RESOLVED: Enforced user.emailVerified check on booking in production with configured email. Verified via tests.
* **Required Regression Tests:** test/booking-pending-limit.test.ts, test/env.test.ts

### Finding ASVS-004: CWE-204: Observable Response Discrepancy (Account Enumeration)
* **Severity:** **Low**
* **ASVS Requirements:** v5.0.0-6.3.3, v5.0.0-13.4.1
* **Affected Files:**
  - `components/auth/auth-form.tsx:L157-L162`
  - `lib/auth.ts:L43-L135`
* **Security Boundary Violated:** Information disclosure / User privacy boundary
* **Exact Code Evidence:** During registration, Better-Auth returns an APIError if the email already exists in the database. The client UI displays 'البريد الإلكتروني مسجل مسبقًا' (Email already registered), enabling an adversary to enumerate existing registered email addresses on the platform.
* **Exploit / Failure Scenario:** An attacker scripts automated POST requests to /api/auth/sign-up/email with target email lists to discover which individuals are registered patients or doctors on Med Aura.
* **Business & Technical Impact:** Low to Moderate privacy risk (disclosure of whether a person uses the cosmetic medical platform).
* **Remediation Strategy:** Protected by reCAPTCHA v3 gating and IP rate limiting (30 reqs/min).
* **Required Regression Tests:** Test verifying rate limiting triggers upon repeated registration attempts.

### Finding ASVS-005: CWE-307: Improper Restriction of Excessive Authentication Attempts / Anti-Automation
* **Severity:** **Low**
* **ASVS Requirements:** v5.0.0-2.4.1, v5.0.0-2.4.2
* **Affected Files:**
  - `lib/actions/booking.ts:L103-L117`
  - `test/booking-pending-limit.test.ts:L1-L60`
* **Security Boundary Violated:** Anti-automation and business logic resource starvation boundary
* **Exact Code Evidence:** Patients could previously book excessive concurrent unpaid appointments holding slots for 15 minutes. Remediated by adding MAX_PENDING_APPOINTMENTS_PER_PATIENT = 3 cap in lib/actions/booking.ts:L103-L117.
* **Exploit / Failure Scenario:** A malicious account scripts rapid booking calls to lock slots across doctors.
* **Business & Technical Impact:** Temporary slot exhaustion until hold expires.
* **Remediation Strategy:** RESOLVED: Added concurrent pending unpaid appointments limit (max 3) in lib/actions/booking.ts:L103-L117. Verified in test/booking-pending-limit.test.ts.
* **Required Regression Tests:** test/booking-pending-limit.test.ts (passed, verifies 3-slot cap).
